# helm — generated, then owned

Spartan primitives generated by `@spartan-ng/cli` and **owned by this library**
(`@lore/ui`), ported from `lore-dam` and `lore-inventory` so both apps share one
styled layer. Plan: `plans/120-design-system-components.md` (D2/D3).

- Brain (`@spartan-ng/brain`, node_modules) is **rented behavior** — never patch it.
- Helm (these files) is **our appearance** — edit freely.
- Components now live in this library, one ng-packagr secondary entry per
  primitive (`projects/ui/helm/<primitive>/`). Import as
  `@lore/ui/helm/<primitive>`. New primitives are generated with
  `@spartan-ng/cli` in a consuming app's scratch tree and ported here by hand —
  the CLI does not write into this workspace, and its tsconfig-path maintenance
  does not apply here (the `@lore/ui/helm/*` path map in `tsconfig.json` covers
  every entry).
- **Never rename generated `hlm*`/`brn*` selectors or class names.** Some primitives
  (select especially) break on selector rename. We edit class strings and templates,
  not identities.

## Restyle checklist (run this on every newly generated primitive)

1. **Semantic utilities only.** `bg-popover`, `text-muted-foreground`, `border-border`,
   `ring-ring`, `bg-destructive` — never raw palette (`bg-zinc-900`). These already
   resolve to lore's tokens through the hlm preset's `@theme inline`, so most colour
   needs zero edits. `@lore/ui/testing`'s token contract is the check.
2. **Density metrics.** Generated helm hard-codes `h-8` / `text-sm`. Rewrite control
   metrics onto the density tokens so `data-density` retunes helm like `.lore-ctl`:
   - height → `h-(--control-h-sm|md|lg)`
   - font-size → `text-(length:--text-ui-sm|md|lg)`
   - spacing → `px-[calc(var(--space)*N)]`, `gap-[calc(var(--space)*N)]`
3. **Motion tokens.** Transition/animation durations → `duration-(--motion-fast)` or
   `duration-(--motion-base)`. Anything animated must respect reduced motion —
   prefer the `motion-safe:` variant (helm often already does this).
4. **Radius: no work.** The preset derives `--radius-sm…4xl` from our base `--radius`.
5. **Shadow audit.** Shadow only on **transient layers** (menus, dialogs, popovers,
   drag previews). Elevation elsewhere = lighter surface + border.
6. **State via data variants.** Use the preset's `data-open:`, `data-checked:`,
   `data-disabled:`, `data-selected:` variants so visuals track the ARIA/data state
   brain maintains. Never strip `data-*`/`aria-*` from a helm template.
7. **Bridge rule.** If a helm template contains something that *is* a lore control
   (dialog/sheet close, tabs paginator, toast action), it takes `loreBtn` / `.lore-ctl`
   + matrix data attributes — **not** shadcn's `buttonVariants`. shadcn variant names
   (`default`/`destructive`/`outline`/`ghost`) must never reach lore's public API.
8. **Never `::ng-deep`** or global CSS against helm internals. These are owned files —
   edit them directly.

## Rulings

- **Target size (120 open question 4).** WCAG 2.2 (2.5.8) floor is 24×24 CSS px and it
  must hold in **compact** density, where `--control-h-sm` is itself exactly 24px.
  Any affordance whose *glyph* is smaller (checkbox at 16px, chip close, table row
  actions) expands its **pointer target** with padding or a `before:absolute
  before:-inset-*` bleed — never by growing the glyph. See `hlm-checkbox.ts`.
- **Two class idioms.** *Matrix* components (button, badge/chip) use `.lore-ctl` +
  `data-variant`/`data-color`/`data-size` styled in `theme/components.css`.
  *Structural/behavioral* helm (dialog frames, menu panels, tables) keeps the
  cva + `hlm()`/`classes()` + Tailwind idiom in these owned files.
- **A field never moves when pressed.** `.lore-ctl:active` translates a control half a
  pixel, except on `input`, `textarea`, `select` and any element carrying the bare
  **`data-field`** attribute (`theme/components.css`). A `<button>` drawn as a field puts
  `data-field` on itself: the date picker and select triggers do, and an app-local
  field-styled trigger (lore-inventory's `HlmUnitSelect`) opts in the same way:
  `<button class="lore-ctl" data-field>`. Presence is the switch; the value is ignored.
- **`HlmTextarea` (`hlmTextarea`) is deprecated.** App code writes `<textarea hlmInput>`
  (`@lore/ui/helm/input`), which sits on `.lore-ctl` like every other control. The
  directive stays because `HlmInputGroupTextarea` hosts it and apps still import it;
  it takes `[aria-invalid]` the same way `HlmInput` does.
- **`HlmButton` (`hlmBtn`) is internal-only.** It exists because `input-group` (a
  dependency of `command`) needs it. App code uses `loreBtn` — the `LoreButton`
  directive, which lives beside it in `@lore/ui/helm/button` — never `hlmBtn`.
- **Hover is never the keyboard's colour.** In a list or menu row (autocomplete,
  combobox, the date picker's month and year lists, dropdown menu items) hover is
  `hover:bg-muted` and keeps the panel's ink; only the keyboard's row
  (`data-highlighted`, or `focus` in a menu) takes `bg-accent`. Brain and the menu's
  focus-on-hover move the highlight to the row a pointer enters, but a key moves it off
  a resting pointer, so an `--accent` hover left two rows painted alike. `hover:` is
  emitted before `focus:` and `data-[highlighted]:`, so a row that is both paints
  `--accent`. `HlmSelectItem` and `HlmCommandItem` carry no hover fill at all. A
  destructive menu item keeps its own wash on hover and focus, inked with
  `--destructive-soft-fg` (`--destructive` on that wash is 3.94:1).
  A calendar day hovers `bg-muted` too, so only today takes `bg-accent`; a hovered
  today or chosen day keeps its own fill, because those rules are emitted later.
  An outside-month day is quieter by colour alone (`text-muted-foreground`, 5.51 / 6.48:1
  on the panel); only a disabled day is faded with `opacity-50`.

## Accordion (`@lore/ui/helm/accordion`)

Built on `@spartan-ng/brain/accordion`. Brain refuses a trigger whose parent is not
`h1`–`h6` (or `role="heading"` with `aria-level`), so the heading level is the caller's:

```html
<hlm-accordion type="multiple">
  <hlm-accordion-item [isOpened]="historyOpen()" (openedChange)="historyOpen.set($event)">
    <h2 hlmAccordionHeader><button hlmAccordionTrigger>History</button></h2>
    <hlm-accordion-content>…</hlm-accordion-content>
  </hlm-accordion-item>
</hlm-accordion>
```

- `type` is brain's and defaults to `single`; pass `multiple` to keep several open.
- `[isOpened]` is one-way. Bind `(openedChange)` back to the same state, or a later
  `true` after the user closes the item changes nothing and so does not reopen it.
- A closed panel stays mounted (brain sets `inert`, the helm clamps it to zero height),
  so its children keep their state and data reads.
- The trigger draws its own chevron and is not a `.lore-ctl`, so it never takes the press.
- Its hover is the plain neutral button's fill (`data-color="neutral"` on the trigger,
  `enabled:hover:bg-(--vc)/10`, `rounded-md`), and nothing stays filled while open. Inline
  padding of `calc(var(--space) * 2)` is pulled back by an equal negative margin, so the
  label lines up with the panel's text. The panel takes no inline padding.

## Autocomplete (`@lore/ui/helm/autocomplete`)

A free-text input with completions, where **the text is the value and the caller owns
it**. Not `HlmCombobox`, which chooses one option and restores its label on Escape.

- Built on CDK's `ActiveDescendantKeyManager` and brain's popover. Brain's
  `BrnAutocompleteSearch` was rejected as the base: its input writes its own value, takes
  a row by replacing the text with the label, and prevents the default action of every
  Enter (brain 1.3.1).
- It never writes the text. `(accept)` hands over the row, the caller splices, passes
  `[text]` back and calls `setCaret(n)`, which focuses the input and places the caret
  after that render. Until then no caret is read: the input still holds the old value
  and caret, and the `text` input does too, so comparing the two cannot catch it.
- The input is an `hlmInput`, so `hlm-field` labels it. Outside a field, use
  `[inputId]` with `<label for>`, or `aria-label`.
- Keys are consumed only while the listbox is on the page, and a consumed key is
  default-prevented **and stopped**. That keeps a surrounding dialog open on the first
  Escape, and the caller's `(keydown)` sees only keys the control did not take.
- No exit animation. The overlay detaches on the next render, so a second Escape
  reaches the dialog straight away.
- Hover and the highlight are two channels: hover is `hover:bg-muted` (neutral) and
  never moves the highlight, and only `data-highlighted` takes `bg-accent` (a primary
  tint), as the table keeps hover off `--accent`. Both rules have the same specificity
  and the highlight's comes later, so a hovered highlighted row paints `--accent`.

## Version note (spartan 1.1)

Helm 1.1 no longer builds host classes with `[class]="hlm(...)"` + `computed()`. It uses
the `classes(() => …)` host-class manager from `@lore/ui/helm/utils`, which merges
with the element's own `class` attribute via tailwind-merge (consumer `class` still
wins). Components that still take an explicit `class` input (e.g. `hlm-select-trigger`)
use `hlm()` + `computed()`. Match whichever idiom the file already uses.
